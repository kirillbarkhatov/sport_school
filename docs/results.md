# Онлайн-результаты (`results`)

Трансляция результатов горнолыжных стартов из протокола (Google Таблица / XLSX) на live-страницу и в
Telegram-канал. Заменяет внешний сервис online_results_script и связку «вебхук → Celery → JSON в StreamRun».

## Как это работает

```
источник (Google Sheets / XLSX / ручной ввод)
   │  results_worker: поток на каждую трансляцию со статусом «Идёт»
   ▼
RawSnapshot (только при изменении) → parse → diff с БД → ResultGroup / ResultEntry + EventLog
   ▼
engine: автофинализация + фокус → ResultsEvent.focus, version++
   ├─► live-страница (опрос фрагмента раз в 3 с; 204, если версия не изменилась)
   └─► Celery: publish_event_to_telegram (одна публикация за раз, изменения не теряются)
```

- **Ядро** — `results/core/`, без Django и IO: `values` (время в мс + статус), `protocol`, `parsing`,
  `engine`, `diff`. Вся логика «закрыт ли заезд» и «какая группа едет» — в `engine.py`.
- **БД — источник правды.** Кнопки «Старт/Пауза/Завершить» меняют статус; воркер замечает это за ~3 с.
  После рестарта воркер сам подхватывает активные трансляции.
- **Ручные правки** времени (`run1_manual`/`run2_manual`) имеют приоритет над источником и пишутся в журнал.
  Снять правку — вернуть значение из протокола.
- **Автофинализация** виртуальная: в источнике ничего не меняется, недостающим ставится DNS при расчёте,
  если не хватает ≤ N участников и на листе стартовала следующая группа или прошёл таймаут.

## Фокус

Лист таблицы — дисциплина/трасса: группы идут по очереди в 1-м заезде, потом все — во 2-м.

- Новое **время** (не статус) двигает фокус на группу этого участника, если это тот же лист и тот же заезд.
- Время с другого листа или из другого заезда **откладывается**, пока текущий заезд не закроется на всём
  листе. Однозаездная группа закрывается сама по себе.
- Без кандидатов фокус ставится на первую начатую и незаконченную группу.

## Запуск

```bash
docker compose up -d results_worker          # в составе стека
poetry run python manage.py results_worker   # локально
```

Для Google-источников нужен ключ сервисного аккаунта с доступом «Читатель» к файлу протокола:
`./secrets/google-service-account.json` (монтируется в `results_worker`), путь меняется через
`RESULTS_GOOGLE_SERVICE_ACCOUNT_FILE`. Тот же ключ, что использует online_results_script.

Публикация в Telegram использует `BOT_TOKEN`; бот должен быть администратором канала.
Минимальный интервал между публикациями — `RESULTS_TELEGRAM_MIN_INTERVAL_SEC` (по умолчанию 2 с).

## Пульт трансляции (`/results/<id>/`)

1. «Проверить источник» — разбор без записи в БД: группы, участники, предупреждения и автоопределённая
   разметка колонок.
2. Если разбор ошибся — скопировать разметку в «Разметка колонок», поправить индексы и сохранить.
3. «Прочитать сейчас» — разовая загрузка; «Старт» — трансляция с опросом.
4. «Связать со спортсменами школы» — по фамилии и имени (+ год рождения, если он есть в протоколе).

Публичная ссылка `/results/public/<token>/` работает, пока трансляция не в черновике и ссылка включена.

## Replay

Каждый изменившийся снимок источника сохраняется. Прогнать трансляцию через текущий движок без записи в БД:

```bash
python manage.py results_replay <id> --standings
```

Так удобно воспроизводить ошибки фокуса и финализации и превращать их в тесты (`results/tests/test_core.py`).

## Отличия от online_results_script

| Было | Стало |
|---|---|
| Отдельный FastAPI-сервис, состояние в памяти, SQLite без привязки к трансляции | Модуль в CRM, всё в Postgres |
| Вебхук + HMAC + повторы + восстановление после рестартов | Прямой вызов внутри процесса |
| Логика заездов и фокуса дублировалась в ORS и Django | Только `results/core/engine.py` |
| Состояние трансляции — один большой JSON | Таблицы групп и участников, журнал с номерами событий |
| Нет тестов разбора | Синтетические протоколы всех форматов, replay |
| Клуб для подсветки захардкожен | Настройка трансляции |
