# Этап 4: план релизов и порядок действий

Исполнительный план введения организаций. Концепция, роли и модель данных — в
[organizations-intro.md](organizations-intro.md), спортсмены и семьи между клубами — в
[athletes-across-orgs.md](athletes-across-orgs.md). Здесь — что именно делаем, в каком порядке, как проверяем
и как выкатываем.

## 0. Общие правила

### Окружения

| Окружение | Где | Ветка | Адрес | Данные |
|---|---|---|---|---|
| Прод | `/srv/projects/sport_school` на сервере `dev`, compose-проект `sport_school` | `dev` (автодеплой GitHub Actions) | `ksclub.ru` | Рабочие |
| Staging | `/srv/projects/sport_school_staging`, compose-проект `sport_school_staging`, порт `127.0.0.1:8020` | Ветка релиза `stage4/rN` | `staging.ksclub.ru` (закрыт паролем) | Копия прода, обновляется скриптом |
| Демо (с R4) | Прод, организация «demo» | `dev` | `demo.ksclub.ru` | Синтетические |

DNS: записи `A @` и `A *` для `ksclub.ru` указывают на `93.100.205.72`. Поддомены не требуют новых DNS-записей.
Каждому поддомену нужен блок nginx и сертификат (HTTP-01 через certbot). Wildcard-сертификат (DNS-01)
понадобится только на этапе 6.

### Ветки и PR

- Под каждый релиз — интеграционная ветка `stage4/rN` от актуального `dev`.
- Каждая задача — отдельный PR в `stage4/rN`. В каждом PR есть тесты, ruff и pre-commit чистые.
- Staging разворачивается из `stage4/rN`. Когда релиз проверен целиком, `stage4/rN` вливается в `dev`,
  и CI выкатывает его на прод.
- `dev` всегда в рабочем состоянии: незаконченные задачи в него не попадают.

### Перед каждой выкаткой на прод

1. Все тесты зелёные (`pytest`), `makemigrations --check` чистый.
2. Staging обновлён свежей копией прода, на нём применены миграции релиза.
3. Сквозные сценарии ([organizations-intro.md](organizations-intro.md#сквозные-сценарии)) пройдены на staging.
4. `manage.py stage4_check --release rN` на staging — без ошибок.
5. Отчёт о релизе (шаблон в конце документа) отправлен владельцу продукта, получено «выкатываем».
6. Бэкап продовой базы: `scripts/backup_db.sh`.
7. Флаги для релиза прописаны в `.env` прода **до** мержа.

### После выкатки

1. CI зелёный, `curl https://ksclub.ru/healthz/` → `{"status": "ok"}`.
2. `manage.py stage4_check --release rN` на проде — без ошибок.
3. Выборочно вручную: вход через бота, карточка семьи, расписание, онлайн-результаты.
4. В README отмечены выполненные пункты.

### Откат

- **Поведение** откатывается флагом в `.env` и `docker compose up -d` (без отката базы).
- **Код** откатывается revert-коммитом мержа в `dev`, миграции обратимы, кроме отмеченных ⚠.
- **Необратимые миграции** (⚠) выкатываются отдельным деплоем после бэкапа и только когда предыдущий шаг
  отработал на проде без замечаний.

### Действия, которые делает владелец сервера

На сервере у пользователя `kb` нет sudo без пароля, поэтому эти шаги выполняет владелец.

| Когда | Что |
|---|---|
| R1, 4.0 | nginx-блок и сертификат для `staging.ksclub.ru` (шаблон `docs/deploy/staging.nginx.conf`), файл паролей для basic auth |
| R3, 4.5 | Тестовый Telegram-бот для staging (BotFather), токен — в `.env` staging |
| R4, 4.9 | nginx-блок и сертификат для `demo.ksclub.ru` |

## R1. Фундамент

**Цель:** появились организации, членство и роли; данные перенесены; поведение для пользователей не изменилось.

### Задачи

**R1-1. Staging и служебные скрипты (4.0)**
- Настройка `STAGING_MODE=True` отключает всё внешнее: Telegram (бот не запускается, публикации не уходят),
  почту (консольный бэкенд), расписание Celery, вызовы AI-сервисов и ассистента, запись в S3
  (на staging `STORAGE_BACKEND=filesystem`). Тест на каждый из этих каналов.
- `scripts/staging_refresh.sh` — дамп продовой базы, восстановление в staging, применение миграций ветки,
  обезличивание контактов (телефоны, email, `tg_id`) по флагу `--anonymize`.
- `scripts/backup_db.sh` — дамп в `backups/` с датой; хранение последних 14.
- `docs/deploy/staging.nginx.conf` — шаблон nginx с basic auth для `staging.ksclub.ru`.
- Раздел про staging в README.

**R1-2. Матрица доступа и инвентаризация (4.0)**
- `tests/access_matrix.py` — таблица «роль × страница/действие → ожидаемый код» для 7 ролей, включая API
  и POST-действия. Известные дыры отмечены `KNOWN_HOLE`: тест проходит и пишет предупреждение.
- `tests/test_model_inventory.py` — каждая модель отнесена к группе: `ORG_OWNED`, `DIRECTORY`, `PLATFORM`,
  `LEGACY`. Новая модель без группы — ошибка.
- `tests/scenarios/` — автоматизированные сквозные сценарии 1–13.

**R1-3. Организации и контекст (4.1)**
- Приложение `organizations`: модели `Organization` (`slug`, название, тип, статус, настройки) и `OrgDomain`
  (хост, основной, подтверждён).
- Миграция данных: организация «ksclub» (тип «клуб»), домены `ksclub.ru` (основной) и `www.ksclub.ru`.
- Middleware ставит `request.organization`; неизвестный хост → `ORGS_DEFAULT_ORGANIZATION_SLUG` (по умолчанию `ksclub`).
- Контекст текущей организации (`contextvars`) с помощниками для Celery (задача принимает `organization_id`,
  задачи по расписанию перебирают активные организации), бота и воркера `results`.
- `Club.organization` и `CompetitionVenue.organization` — необязательные ссылки; «Канаев Ски Клаб» → «ksclub».

**R1-4. Членство и роли (4.2)**
- Модели `Membership`, `OrgRole`, `RoleAssignment`, `PlatformRole`, `AuditLog`.
- Системные роли организации: владелец, администратор, менеджер, тренер, секретарь соревнований.
  Глобальные роли: глобальный администратор, поддержка.
- Команда `manage.py orgs_import_legacy` — идемпотентный перенос:
  - пользователь → членство в «ksclub»: `is_approved` → активен, иначе ждёт;
  - группы «Администратор», «Менеджер», «Тренер» → роли;
  - `TELEGRAM_ADMIN_IDS`, `TELEGRAM_MANAGER_IDS`, `TELEGRAM_COACH_IDS` → роли пользователей с этими `tg_id`;
  - суперпользователь → глобальный администратор и владелец «ksclub»;
  - `is_staff` без суперпользователя → администратор «ksclub».

  Это команда, а не миграция, потому что зависит от `.env`. Запускается в шаге `migrate` после миграций.
- Двойная запись (`ORGS_LEGACY_SYNC=True`): `is_approved`, группы и `is_staff` пересчитываются из членства
  и ролей; изменение групп в старой админке пересчитывается в роли.
- `manage.py orgs_report` — сводка: пользователи, членства по статусам, роли, расхождения со старыми полями.

**R1-5. Проверка релиза**
- `manage.py stage4_check --release r1`: организация «ksclub» и её домены есть; у каждого пользователя есть
  членство; роли совпадают со старыми полями; контекст организации есть у каждой задачи по расписанию.

### Флаги R1

```
ORGS_DEFAULT_ORGANIZATION_SLUG=ksclub
ORGS_LEGACY_SYNC=True
ORGS_ROLES_SOURCE=legacy
```

### Выкатка R1

1. Владелец сервера настраивает nginx и сертификат для `staging.ksclub.ru`.
2. `scripts/staging_refresh.sh --anonymize`, деплой `stage4/r1` на staging, `migrate`, `orgs_import_legacy`.
3. Матрица доступа и сценарии на staging; `orgs_report` сверен вручную.
4. Отчёт → «выкатываем» → бэкап → флаги в `.env` прода → мерж `stage4/r1` в `dev`.
5. После деплоя: `orgs_import_legacy` (в шаге `migrate`), `stage4_check --release r1`, выборочная ручная проверка.

**Готово, когда:** матрица доступа не изменилась; членств столько же, сколько пользователей; сценарии
зелёные на staging и проде.

**Откат:** новые таблицы никто не читает — revert безопасен.

## R2. Права и данные

**Цель:** права проверяются через членство и роли, все данные принадлежат организации, вторая организация
изолирована, внешние спортсмены и выпускники обработаны. Пользователи замечают только исправленные дыры
и уход внешних спортсменов из рабочих списков.

### Задачи

**R2-1. Слой прав (4.3)**
- `organizations/permissions.py`: `authorize(user, action, obj=None)`, `visible_to(user, action, queryset)`,
  каталог действий для текущих ролей.
- Старые помощники вызывают новый слой: `ApprovedUserRequiredMixin`, `user_is_admin/manager/coach`
  в боте, `_can_manage_online_results`, `can_manage_results`, проверки `is_staff` в представлениях.
- Флаг `ORGS_ROLES_SOURCE`: `legacy` — старые поля, `memberships` — новый слой. Матрица доступа проходит
  при обоих значениях.

**R2-2. Исправление дыр (4.3)**
- Создание и редактирование соревнований, занятий, групп, загрузка документов, AI-анализ, выгрузки — только
  сотрудникам. Отметки `KNOWN_HOLE` снимаются, ожидания в матрице меняются в том же PR.
- Роли из `TELEGRAM_*_IDS` больше не читаются. Переменные удаляются из `.env` после выкатки.

**R2-3. Организация в данных: добавить и заполнить (4.4)**
- Абстрактная модель `OrgOwned` (поле `organization`, менеджер `for_org`, заполнение из контекста при сохранении).
- Необязательное поле `organization` во всех моделях группы `ORG_OWNED` (по одной миграции на приложение)
  и миграции данных, проставляющие «ksclub».

**R2-4. Фильтрация по организации (4.4)**
- Представления, формы (выпадающие списки), API, выгрузки, задачи Celery, обработчики бота, воркер `results`
  и публичные страницы — через `for_org(...)` / `visible_to(...)`.
- Флаг `ORGS_ENFORCE_SCOPING`.
- Тест изоляции: фикстура второй организации с полным набором данных. Пользователь «ksclub» не видит
  её данных ни на одной странице, ни в API, ни в выгрузке, ни в боте, ни в задаче — и наоборот.

**R2-5. Внешние спортсмены и выпускники (4.4a)**
- Поле `Person.is_external` и миграция по правилу: клуб не «Канаев Ски Клаб» и нет группы, семьи
  и договора в «ksclub».
- Внешние исключены из рабочих списков, поиска и рассылок; фильтр «Внешние спортсмены»; заявки и результаты
  их видят.
- `manage.py orgs_externals_report` — внешние, люди без клуба, внешние с контактами или документами.
- Семьи-выпускники: членство связанных пользователей → «ушёл», доступ к своей истории только на чтение
  (настройка организации).

**R2-6. Обязательное поле организации ⚠ (4.4)**
- Поле `organization` становится обязательным; глобальные уникальности → уникальные внутри организации.
- Отдельный деплой после того, как R2-1…R2-5 отработали на проде.

**R2-7. Проверка релиза**
- `stage4_check --release r2`: нет строк без организации; все представления и задачи проходят через фильтр
  (по реестру из теста инвентаризации); отчёт по внешним сформирован.

### Флаги R2

```
ORGS_ROLES_SOURCE=legacy        # → memberships после проверки на проде
ORGS_ENFORCE_SCOPING=False      # → True после проверки на проде
```

### Выкатка R2 (по шагам, каждый — отдельный деплой)

1. Деплой R2-1…R2-5 с `ORGS_ROLES_SOURCE=legacy`, `ORGS_ENFORCE_SCOPING=False`. Проверка: сценарии.
2. `ORGS_ROLES_SOURCE=memberships` → перезапуск → матрица и сценарии на проде.
3. `ORGS_ENFORCE_SCOPING=True` → перезапуск → сценарии на проде.
4. Разбор отчёта по внешним с владельцем продукта.
5. Бэкап → деплой R2-6 (⚠) → `stage4_check --release r2`.

**Готово, когда:** матрица с осознанными изменениями; тест изоляции зелёный; нет данных без организации;
отчёт по внешним разобран; сценарии зелёные.

**Откат:** шаги 2–3 — флагами; R2-6 — восстановлением из бэкапа (поэтому идёт последним).

## R3. Вход и администрирование

**Цель:** единый вход, консоль платформы, администрирование организации в интерфейсе, посетители.
Django-админка — только для глобальных администраторов.

### Задачи

**R3-1. Единый вход (4.5)**
- Модель `AuthIdentity`; миграция данных из `tg_id` и email.
- Вход через бота (одноразовый токен) и ссылки `xfer` переносятся в модуль `organizations.auth`;
  для пользователя всё как раньше.
- Одноразовый код для заведения сессии на адресе организации: `/auth/handoff/`. Центральный адрес входа —
  настройка `ORGS_CENTRAL_LOGIN_HOST` (пусто: вход на адресе самой организации).
- Бот понимает организацию: `?start=<slug>`, выбор организации при нескольких активных членствах,
  уведомления и меню — в контексте организации.
- Проверка на staging с тестовым ботом.

**R3-2. Консоль платформы (4.6)**
- `/platform/` для глобальных администраторов: организации (создать, приостановить), владельцы через
  приглашение, домены, журнал платформы, режим поддержки и «войти как пользователь» — с записью в журнал.
- В интерфейсе появляются действия, которые сейчас делаются только в Django-админке (по журналу за год):
  управление пользователями, удаление людей, удаление соревнований — с подтверждением и журналом.
- `AdminSite.has_permission` — только глобальные администраторы.

**R3-3. Администрирование организации (4.7)**
- Настройки организации: название, логотип, часовой пояс.
- Сотрудники и роли: список, смена роли, приостановка, приглашение по ссылке или в боте.
- Очередь заявок участников вместо «ожидает одобрения»: подтверждение и связь с `Person`. Существующие
  ожидающие попадают в очередь. Старая страница остаётся за флагом `ORGS_LEGACY_APPROVAL_PAGE` до R4.
- Журнал организации.

**R3-4. Посетители (4.8)**
- Публичные страницы (онлайн-результаты, заявки на соревнования) определяют организацию по адресу и не
  требуют членства.
- Вошедший пользователь без членства видит публичную часть и «Вступить / я родитель» — это создаёт заявку
  в очереди R3-3.

**R3-5. Проверка релиза**
- `stage4_check --release r3`: у каждого пользователя с `tg_id` есть `AuthIdentity`; в Django-админку пускает
  только глобальных администраторов; ожидающие пользователи в очереди заявок.

### Флаги R3

```
ORGS_CENTRAL_LOGIN_HOST=
ORGS_LEGACY_APPROVAL_PAGE=True   # → False после проверки очереди заявок на проде
```

### Выкатка R3

1. Владелец сервера создаёт тестового бота и кладёт токен в `.env` staging.
2. Staging: вход через тестового бота и `xfer`, приглашение сотрудника, подтверждение родителя, заявка
   посетителя, консоль платформы, закрытая админка.
3. Отчёт → «выкатываем» → бэкап → мерж.
4. После деплоя: вход через бота на проде, администратор «ksclub» проходит очередь заявок;
   `ORGS_LEGACY_APPROVAL_PAGE=False`.

**Готово, когда:** вход работает как раньше; администратор организации управляет людьми в интерфейсе;
админка закрыта для всех, кроме глобальных администраторов; сценарии зелёные.

**Откат:** флаг `ORGS_LEGACY_APPROVAL_PAGE`; revert мержа (миграции обратимы).

## R4. Вторая организация и уборка

**Цель:** вторая организация на проде изолирована; старые механизмы удалены; включена защита на уровне базы.

### Задачи

**R4-1. Демо-организация (4.9)**
- `manage.py orgs_create_demo` — организация «demo» на `demo.ksclub.ru` с синтетическими данными: семьи,
  группы, занятия, трансляция результатов.
- Владелец сервера: nginx и сертификат для `demo.ksclub.ru`.
- На проде: тест изоляции (автоматический прогон против `ksclub.ru` и `demo.ksclub.ru` под учётками обеих
  организаций), матрица доступа для демо.

**R4-2. Уборка (4.10)**
- Удалить чтения старых полей и двойную запись: `is_approved`, группы Django как роли, `TELEGRAM_*_IDS`,
  старые страницы входа и «ожидает одобрения», флаги `ORGS_LEGACY_*` и `ORGS_ROLES_SOURCE`.
- Неизвестный адрес → страница «организация не найдена»; `ORGS_DEFAULT_ORGANIZATION_SLUG` удаляется.

**R4-3. Row-Level Security ⚠ (4.10)**
- Политики RLS для внутренних таблиц (люди, семьи, договоры, платежи, документы); организация передаётся
  в соединение (`SET app.current_org`) из middleware и контекста задач.
- Сначала staging с полным прогоном сценариев, затем прод отдельным деплоем после бэкапа. Миграция
  обратима (политики удаляются).

**R4-4. Проверка релиза**
- `stage4_check --release r4`: обе организации изолированы; старых флагов нет; RLS включён для перечисленных таблиц.

### Выкатка R4

1. Демо на staging (`demo.staging` не нужен — проверка по заголовку Host), затем на проде.
2. Уборка R4-2 — деплой; сценарии.
3. RLS R4-3 — бэкап, деплой, сценарии и тест изоляции на проде.

**Готово, когда:** выполнены критерии [готовности этапа 4](organizations-intro.md#готовность-этапа-4).
