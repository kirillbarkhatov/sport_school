# Введение организаций: плавный переход

Как перевести работающую систему одного клуба на модель организаций так, чтобы на каждом шаге всё
работало как раньше, каждый шаг выкатывался отдельно и откатывался флагом. Целевая архитектура —
в [platform.md](platform.md), план работ — в [README](../README.md#план-работ), этап 4.

## Принципы

- **Сначала одна организация.** Все текущие данные принадлежат организации «ksclub». Пока не появится
  вторая организация, пользователи не замечают изменений: те же адреса, тот же вход через бота, те же страницы.
- **Расширить → заполнить → переключить → убрать.** Новые структуры появляются рядом со старыми, данные
  переносятся миграцией, код переключается на новые структуры, и только потом старые поля удаляются.
- **Каждый шаг — отдельный деплой с флагом.** Флаги `ORGS_*` позволяют откатить поведение без отката базы.
- **Проверяем на копии прода.** Перед каждой миграцией данных — прогон на staging с дампом продовой базы.
- **Матрица доступа фиксирует поведение.** До изменений записываем, кто что видит сейчас. Каждый шаг либо
  её не меняет, либо меняет осознанно, с правкой ожиданий в тестах.

## Кто есть кто

| Кто | Где действует | Что может |
|---|---|---|
| **Глобальный администратор** | Вся платформа | Создавать и приостанавливать организации, назначать владельцев, управлять доменами, видеть журнал платформы. В закрытые данные организации входит только в режиме поддержки, с записью в журнал |
| **Поддержка платформы** | Вся платформа | Смотреть настройки организаций и состояние сервисов, «войти как пользователь» с записью в журнал. Ничего не меняет без режима поддержки |
| **Владелец организации** | Своя организация | Всё в организации, включая передачу владения и удаление. Владелец всегда есть хотя бы один |
| **Администратор организации** | Своя организация | Всё, кроме владения: настройки, сотрудники и роли, подтверждение участников, все разделы |
| **Сотрудник** (менеджер, тренер, секретарь соревнований…) | Своя организация, позже — с областью действия | Разделы по роли, как сейчас у групп «Менеджер» и «Тренер» |
| **Участник** (родитель, спортсмен) | Организация, где он подтверждён | Свои дети или свой профиль: расписание, договоры, документы, результаты |
| **Посетитель** | Публичные страницы любой организации | Без входа — публичные страницы (онлайн-результаты, заявки на соревнования, позже календарь). С входом, но без членства — то же, плюс заявка «я родитель / я спортсмен этой организации» |

Глобальная роль и роль в организации — разные вещи. Глобальный администратор не становится
автоматически администратором каждой организации, а администратор организации не получает доступа
к другим организациям и к Django-админке.

## Что меняется в модели данных

### Новые сущности

| Сущность | Назначение |
|---|---|
| `Organization` | `slug`, название, тип (клуб, федерация, база, платформа), статус (активна, приостановлена), настройки (часовой пояс, логотип, вид спорта) |
| `OrgDomain` | Адрес организации: хост, основной ли, подтверждён ли. Для «ksclub» — `ksclub.ru` и `www.ksclub.ru` |
| `Membership` | Пользователь ↔ организация: статус (приглашён, ждёт подтверждения, активен, приостановлен), когда вступил, кто подтвердил |
| `OrgRole` | Роль в организации: владелец, администратор, менеджер, тренер, секретарь; позже — свои роли организации |
| `RoleAssignment` | Membership ↔ роль. На этапе 4 — на всю организацию; область действия (филиал, группы, соревнование) появится на этапе 5 |
| `PlatformRole` | Глобальные роли пользователя: глобальный администратор, поддержка |
| `AuthIdentity` | Способ входа пользователя: Telegram (`tg_id`), email, позже телефон и passkey |
| `Invitation` | Приглашение в организацию с ролью: ссылка или сообщение в боте, срок действия |
| `AuditLog` | Кто, что, где и когда: изменения ролей и членства, режим поддержки, вход «как пользователь» |

### Что остаётся как есть

- **`users.User` остаётся учётной записью платформы.** Замена `AUTH_USER_MODEL` на живой базе рискованна
  и ничего не даёт: одна запись `User` на человека — это и есть `Account` из целевой модели.
- **`Person`, семьи, договоры** остаются внутри организации, только получают ссылку на неё.
- **Вход через Telegram-бота** по одноразовому токену и ссылки `xfer` продолжают работать без изменений
  для пользователя.

### Классификация таблиц

| Группа | Таблицы | Что происходит |
|---|---|---|
| Данные организации | `Person`, `Athlete`, `Coach`, `PotentialClient`, `Group`, `Class`, `ClassEnrollment`, `TrainingCamp`, `CampEnrollment`, `TrainingTemplate`, `Family*`, `AthleteContract`, `FamilyService`, `FamilyPayment`, `Document*`, `AthleteDocument`, `Competition*` (заявки, участники, документы, группы зачёта), `Notification`, `results.*`, `PersonDedup*`, `WhatsAppChat*`, `TrainingReminderLog`, `UserPersonLink`, `UserAthleteLink` | Получают `organization`; запросы фильтруются по текущей организации |
| Справочники (будущие организации) | `Club`, `CompetitionVenue` | Получают необязательную ссылку на `Organization`. Строка «своего» клуба связывается с «ksclub». Остальные — «незанятые» карточки, которые клубы и базы заберут себе на этапе 7 |
| Платформа | `User`, `TelegramChat`, `TelegramParticipant`, `assistant.ServiceAccount` | Остаются глобальными; чаты бота и сервисные учётные записи получают ссылку на организацию, если привязаны к ней |
| Наследие | `api.StreamRun`, `WebhookEvent`, `PublicStreamAccess` | Получают `organization` ради истории, новой логики не появляется |

## Шаги

Каждый шаг — отдельный PR, деплой и проверка на staging. Шаги 4.1–4.4 не меняют поведение для пользователей.

### 4.0. Подготовка

- Staging: второй compose-проект на сервере, дамп прода, отдельный поддомен.
- Матрица доступа: тесты «роль × страница → ожидаемый ответ» на текущем поведении, включая известные
  дыры (родитель открывает формы редактирования). Они помечаются как ожидаемо неверные и исправляются на 4.3.
- Инвентаризация: таблица выше превращается в тест, который падает, если у модели данных организации нет
  поля `organization` (после шага 4.4).

### 4.1. Организации и контекст запроса

- Модели `Organization`, `OrgDomain`. Миграция данных создаёт «ksclub» и домены `ksclub.ru`, `www.ksclub.ru`.
- Middleware ставит `request.organization` по хосту. Неизвестный хост (localhost, IP, старые адреса) →
  организация по умолчанию `DEFAULT_ORGANIZATION_SLUG`, поэтому ничего не ломается.
- Контекст организации в Celery-задачах и в боте: задача получает `organization_id`, задачи по расписанию
  перебирают активные организации. Пока организация одна, поведение то же.
- Справочники `Club` и `CompetitionVenue` получают ссылку на организацию; свой клуб связывается с «ksclub».

### 4.2. Членство и роли рядом со старыми флагами

- Модели `Membership`, `OrgRole`, `RoleAssignment`, `PlatformRole`, `AuditLog`.
- Миграция данных:
  - каждый пользователь → членство в «ksclub»: `is_approved` → активен, иначе ждёт подтверждения;
  - группа «Администратор» → роль администратора, «Менеджер» → менеджер, «Тренер» → тренер;
  - пользователи из `TELEGRAM_ADMIN_IDS` / `TELEGRAM_MANAGER_IDS` / `TELEGRAM_COACH_IDS` → те же роли;
  - суперпользователи → глобальные администраторы и владельцы «ksclub» (владельца можно сменить позже);
  - `is_staff` без суперпользователя → администратор «ksclub».
- **Двойная запись:** членство и роли — источник правды, а `is_approved`, группы Django и `is_staff`
  обновляются из них автоматически, пока старый код их читает. Изменение группы в старой админке тоже
  пересчитывается в роль, чтобы данные не разъехались.

### 4.3. Слой прав поверх старых проверок

- `authorize(user, action, obj=None)` и `visible_to(user, action)` на основе членства и ролей в текущей организации.
- Старые помощники (`ApprovedUserRequiredMixin`, `user_is_admin`, `user_is_manager`, `user_is_coach`,
  `_can_manage_online_results`, проверки `is_staff`) внутри вызывают новый слой с той же логикой.
  Матрица доступа не меняется.
- Затем осознанно исправляются дыры: формы создания и редактирования, загрузка документов и выгрузки —
  только сотрудникам. Ожидания в матрице меняются в том же PR.
- Списки ID в `.env` перестают быть источником ролей: роли только в базе. Переменные удаляются после
  проверки на проде.

### 4.4. Организация в данных

- **Расширить:** необязательное поле `organization` во всех таблицах данных организации.
- **Заполнить:** миграция данных проставляет «ksclub» (база ~25 МБ, это секунды).
- **Переключить:** абстрактная модель `OrgOwned` с менеджером `for_org(...)`; при сохранении организация
  берётся из контекста запроса или задачи. Представления, задачи и бот переходят на запросы с фильтром по организации.
- **Закрепить:** поле становится обязательным; уникальности, которые сейчас глобальные, становятся
  уникальными внутри организации.
- Тест изоляции: две организации с данными, пользователь одной не видит ничего из другой ни на одной
  странице и ни в одном API.
- **Внешние спортсмены.** Люди и спортсмены других клубов, загруженные из протоколов, остаются в «ksclub»
  с пометкой «внешний» и уходят из рабочих списков и рассылок. Семьи-выпускники: членство родителей →
  «ушёл», история только на чтение. Подробно — [athletes-across-orgs.md](athletes-across-orgs.md).

### 4.5. Единый вход

- `AuthIdentity` заполняется из `tg_id` и email. Вход через бота и `xfer` переводятся на новый модуль
  без изменений для пользователя.
- Схема «вход на одном адресе → одноразовый код → сессия на адресе организации». Пока адрес один
  (`ksclub.ru`), код используется только внутри него. Когда появится центральный адрес входа
  (`id.<platform>`), его включение — изменение настройки, а не новая разработка.
- Бот понимает организацию: `?start=<slug>`, по умолчанию «ksclub». Если человек состоит в нескольких
  организациях, бот предлагает выбрать.
- Проверка локально на двух адресах (`ksclub.localhost` и `id.localhost`).

### 4.6. Консоль платформы

- Раздел глобального администратора `/platform/` на адресе платформы (до выбора домена — на `ksclub.ru`
  для глобальных администраторов):
  - список организаций, создание (тип, slug, домен), приостановка;
  - назначение владельца через приглашение;
  - домены организаций и их подтверждение;
  - журнал платформы;
  - режим поддержки и «войти как пользователь», всё с записью в журнал.
- Django-админка — только глобальным администраторам. Сотрудники организаций работают в интерфейсе
  приложения; всё, что они сейчас делают в админке, переносится в интерфейс до закрытия доступа.

### 4.7. Администрирование организации

- Настройки организации: название, логотип, часовой пояс.
- Сотрудники и роли: приглашение по ссылке или в боте, смена роли, приостановка доступа.
- Очередь подтверждения участников вместо страницы «ожидает одобрения». Родитель отправляет заявку
  «это мой ребёнок», администратор подтверждает и связывает с `Person`.
- Журнал организации: изменения ролей, членства, подтверждения.

### 4.8. Посетители и публичные страницы

- Публичные страницы (онлайн-результаты, ссылки на заявки, позже календарь) определяют организацию по
  адресу и открываются без членства.
- Вошедший пользователь без членства в текущей организации видит публичную часть и кнопку
  «Вступить / я родитель» — это создаёт заявку на членство.
- Подписки посетителей (на спортсмена, старт, клуб) — на этапе 8. Здесь достаточно того, что посетитель —
  это пользователь без членства, и система это корректно различает.

### 4.9. Вторая организация

- Демо-организация на временном поддомене текущего домена (например, `demo.ksclub.ru`). Выбор домена
  платформы на этом шаге ещё не нужен.
- Прогон матрицы доступа и теста изоляции на проде с двумя организациями.
- Пилотная реальная организация (второй клуб, федерация или база).

### 4.10. Уборка

- Удаляются чтения `is_approved`, групп Django как ролей и списков ID в `.env`; двойная запись выключается.
- Организация по умолчанию для неизвестных хостов отключается: неизвестный адрес → страница «организация
  не найдена».
- Row-Level Security в Postgres для внутренних таблиц (люди, договоры, платежи, медицина).

## Флаги

| Флаг | Что включает | Когда включаем |
|---|---|---|
| `ORGS_DEFAULT_ORGANIZATION_SLUG` | Организация для неизвестных хостов | 4.1, выключается на 4.10 |
| `ORGS_ENFORCE_SCOPING` | Фильтрация запросов по организации | 4.4, после теста изоляции |
| `ORGS_ROLES_SOURCE` | Откуда читать роли: `legacy`, `memberships` | 4.3: сначала `legacy`, затем `memberships` |
| `ORGS_LEGACY_SYNC` | Двойная запись в `is_approved` и группы | 4.2–4.10 |
| `ORGS_CENTRAL_LOGIN_HOST` | Центральный адрес входа | 4.5 (пусто), включается при выборе домена платформы |

## Риски и как их снимаем

| Риск | Защита |
|---|---|
| Забытый фильтр по организации — утечка данных | Тест изоляции на двух организациях, тест инвентаризации, позже RLS |
| Ошибка в миграции ролей — кто-то потеряет доступ | Прогон на staging с дампом прода, сравнение матрицы доступа до и после, флаг `ORGS_ROLES_SOURCE=legacy` для отката |
| Задачи по расписанию без организации | Задачи получают `organization_id` явно, тест на каждую задачу |
| Бот путает организации | Организация в `start`-параметре, выбор при нескольких членствах, тесты обработчиков |
| Сотрудники теряют Django-админку раньше, чем есть замена | Закрываем админку только после переноса нужных действий в интерфейс (4.6–4.7) |

## Что нужно решить до начала

- Кто владелец «ksclub» после миграции (предложение: текущий суперпользователь, сменить можно в 4.7).
- Какие действия сотрудники сейчас выполняют в Django-админке — их нужно перенести в интерфейс до 4.6.
- Пилот для шага 4.9: второй клуб, федерация или база.
- Домен платформы нужен только для центрального входа и поддоменов организаций. Этап 4 можно пройти
  на `ksclub.ru`, а демо-организацию разместить на его поддомене.
