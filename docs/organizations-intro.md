# Введение организаций: плавный переход

Как перевести работающую систему одного клуба на модель организаций так, чтобы на каждом шаге всё
работало как раньше, каждый шаг выкатывался отдельно и откатывался флагом. Целевая архитектура —
в [platform.md](platform.md), план работ — в [README](../README.md#план-работ), этап 4.

## Принципы

- **Сначала одна организация.** Все текущие данные принадлежат организации «ksclub». Пока не появится
  вторая организация, пользователи не замечают изменений: те же адреса, тот же вход через бота, те же страницы.
- **Расширить → заполнить → переключить → убрать.** Новые структуры появляются рядом со старыми, данные
  переносятся миграцией, код переключается на новые структуры, и только потом старые поля удаляются.
- **Каждый шаг — отдельный деплой с флагом.** Флаги `ORGS_*` позволяют откатить поведение без отката базы.
- **Проверяем на копии прода.** Перед каждой миграцией данных — прогон на staging с дампом продовой базы.
- **Матрица доступа фиксирует поведение.** До изменений записываем, кто что видит сейчас. Каждый шаг либо
  её не меняет, либо меняет осознанно, с правкой ожиданий в тестах.

## Кто есть кто

| Кто | Где действует | Что может |
|---|---|---|
| **Глобальный администратор** | Вся платформа | Создавать и приостанавливать организации, назначать владельцев, управлять доменами, видеть журнал платформы. В закрытые данные организации входит только в режиме поддержки, с записью в журнал |
| **Поддержка платформы** | Вся платформа | Смотреть настройки организаций и состояние сервисов, «войти как пользователь» с записью в журнал. Ничего не меняет без режима поддержки |
| **Владелец организации** | Своя организация | Всё в организации, включая передачу владения и удаление. Владелец всегда есть хотя бы один |
| **Администратор организации** | Своя организация | Всё, кроме владения: настройки, сотрудники и роли, подтверждение участников, все разделы |
| **Сотрудник** (менеджер, тренер, секретарь соревнований…) | Своя организация, позже — с областью действия | Разделы по роли, как сейчас у групп «Менеджер» и «Тренер» |
| **Участник** (родитель, спортсмен) | Организация, где он подтверждён | Свои дети или свой профиль: расписание, договоры, документы, результаты |
| **Посетитель** | Публичные страницы любой организации | Без входа — публичные страницы (онлайн-результаты, заявки на соревнования, позже календарь). С входом, но без членства — то же, плюс заявка «я родитель / я спортсмен этой организации» |

Глобальная роль и роль в организации — разные вещи. Глобальный администратор не становится
автоматически администратором каждой организации, а администратор организации не получает доступа
к другим организациям и к Django-админке.

## Что меняется в модели данных

### Новые сущности

| Сущность | Назначение |
|---|---|
| `Organization` | `slug`, название, тип (клуб, федерация, база, платформа), статус (активна, приостановлена), настройки (часовой пояс, логотип, вид спорта) |
| `OrgDomain` | Адрес организации: хост, основной ли, подтверждён ли. Для «ksclub» — `ksclub.ru` и `www.ksclub.ru` |
| `Membership` | Пользователь ↔ организация: статус (приглашён, ждёт подтверждения, активен, приостановлен), когда вступил, кто подтвердил |
| `OrgRole` | Роль в организации: владелец, администратор, менеджер, тренер, секретарь; позже — свои роли организации |
| `RoleAssignment` | Membership ↔ роль. На этапе 4 — на всю организацию; область действия (филиал, группы, соревнование) появится на этапе 5 |
| `PlatformRole` | Глобальные роли пользователя: глобальный администратор, поддержка |
| `AuthIdentity` | Способ входа пользователя: Telegram (`tg_id`), email, позже телефон и passkey |
| `Invitation` | Приглашение в организацию с ролью: ссылка или сообщение в боте, срок действия |
| `AuditLog` | Кто, что, где и когда: изменения ролей и членства, режим поддержки, вход «как пользователь» |

### Что остаётся как есть

- **`users.User` остаётся учётной записью платформы.** Замена `AUTH_USER_MODEL` на живой базе рискованна
  и ничего не даёт: одна запись `User` на человека — это и есть `Account` из целевой модели.
- **`Person`, семьи, договоры** остаются внутри организации, только получают ссылку на неё.
- **Вход через Telegram-бота** по одноразовому токену и ссылки `xfer` продолжают работать без изменений
  для пользователя.

### Классификация таблиц

| Группа | Таблицы | Что происходит |
|---|---|---|
| Данные организации | `Person`, `Athlete`, `Coach`, `PotentialClient`, `Group`, `Class`, `ClassEnrollment`, `TrainingCamp`, `CampEnrollment`, `TrainingTemplate`, `Family*`, `AthleteContract`, `FamilyService`, `FamilyPayment`, `Document*`, `AthleteDocument`, `Competition*` (заявки, участники, документы, группы зачёта), `Notification`, `results.*`, `PersonDedup*`, `WhatsAppChat*`, `TrainingReminderLog`, `UserPersonLink`, `UserAthleteLink` | Получают `organization`; запросы фильтруются по текущей организации |
| Справочники (будущие организации) | `Club`, `CompetitionVenue` | Получают необязательную ссылку на `Organization`. Строка «своего» клуба связывается с «ksclub». Остальные — «незанятые» карточки, которые клубы и базы заберут себе на этапе 7 |
| Платформа | `User`, `TelegramChat`, `TelegramParticipant`, `assistant.ServiceAccount` | Остаются глобальными; чаты бота и сервисные учётные записи получают ссылку на организацию, если привязаны к ней |
| Наследие | `api.StreamRun`, `WebhookEvent`, `PublicStreamAccess` | Получают `organization` ради истории, новой логики не появляется |

## Релизы

Этап 4 выкатывается **четырьмя релизами**. После каждого система полностью рабочая: все текущие сценарии
работают, а новое либо невидимо для пользователей, либо уже готово целиком. Внутри релиза может быть
несколько PR, но на сервер он выходит, только когда проверен целиком.

| Релиз | Шаги | Что заметят пользователи | Оценка |
|---|---|---|---|
| **R1. Фундамент** | 4.0–4.2 | Ничего | 1,5–2 нед. |
| **R2. Права и данные** | 4.3–4.4a | Родители больше не видят формы редактирования; внешние спортсмены ушли из рабочих списков | 2–3 нед. |
| **R3. Вход и администрирование** | 4.5–4.8 | Администратор клуба управляет сотрудниками и заявками в интерфейсе; посетители могут попроситься в клуб | 2–3 нед. |
| **R4. Вторая организация и уборка** | 4.9–4.10 | Ничего для ksclub; появляется демо-организация | 1 нед. |

### R1. Фундамент (без изменения поведения)

**4.0. Подготовка**
- Staging на сервере `dev`: отдельный compose-проект с копией продовой базы и своим портом. Каждая миграция
  данных сначала прогоняется там.
- Матрица доступа: тесты «роль × страница → ожидаемый ответ» на текущем поведении. Известные дыры
  (родитель открывает формы редактирования) помечены как ожидаемо неверные, исправляются в R2.
- Сквозные сценарии (список ниже) оформлены как автоматический прогон на staging.
- Тест инвентаризации: каждая модель отнесена к одной из групп таблицы выше; новая модель без классификации — ошибка.

**4.1. Организации и контекст**
- `Organization`, `OrgDomain`; миграция создаёт «ksclub» с доменами `ksclub.ru` и `www.ksclub.ru`.
- Middleware: `request.organization` по хосту; неизвестный хост → «ksclub» (флаг `ORGS_DEFAULT_ORGANIZATION_SLUG`).
- Контекст организации в Celery (параметр `organization_id`, задачи по расписанию перебирают активные
  организации), в боте и в воркере `results`.
- `Club` и `CompetitionVenue` получают необязательную ссылку на организацию; «Канаев Ски Клаб» → «ksclub».

**4.2. Членство и роли рядом со старыми флагами**
- `Membership`, `OrgRole`, `RoleAssignment`, `PlatformRole`, `AuditLog`.
- Миграция: пользователи → членство в «ksclub» (`is_approved` → активен, иначе ждёт); группы и списки ID
  из `.env` → роли; суперпользователи → глобальные администраторы и владельцы «ksclub»; `is_staff` →
  администратор «ksclub».
- Двойная запись: старые поля (`is_approved`, группы, `is_staff`) обновляются из членства и ролей
  (флаг `ORGS_LEGACY_SYNC`). Чтения прав остаются старыми (`ORGS_ROLES_SOURCE=legacy`).

**Проверка R1:** матрица доступа не изменилась; число членств равно числу пользователей; отчёт миграции ролей
сверен вручную; сквозные сценарии зелёные на staging и после выкатки.

**Откат R1:** новые таблицы никто не читает, откат кода безопасен; миграции обратимы.

### R2. Права и данные

**4.3. Слой прав**
- `authorize` / `visible_to` на членстве и ролях. Старые помощники (`ApprovedUserRequiredMixin`,
  `user_is_admin/manager/coach`, `_can_manage_online_results`, проверки `is_staff`) вызывают новый слой.
- Переключение `ORGS_ROLES_SOURCE=memberships` — матрица та же.
- Исправление дыр: создание и редактирование соревнований, занятий, групп, загрузка документов, выгрузки —
  только сотрудникам. Ожидания в матрице меняются в том же PR.
- Роли только из базы; переменные `TELEGRAM_*_IDS` больше не дают ролей.

**4.4. Организация в данных**
- Добавить необязательное поле → заполнить «ksclub» → перевести представления, задачи, бот, API и `results`
  на запросы с фильтром по организации → сделать поле обязательным; уникальности — внутри организации.
- `ORGS_ENFORCE_SCOPING` включается после теста изоляции: две организации с данными, пользователь одной
  не видит ничего из другой ни на одной странице, ни в API, ни в выгрузках, ни в боте.

**4.4a. Внешние спортсмены и выпускники**
- Пометка «внешний»: клуб в карточке не «Канаев Ски Клаб» и нет группы, семьи и договора в «ksclub».
  Внешние уходят из рабочих списков и рассылок, остаются в заявках и результатах, есть фильтр «Внешние».
- Отчёт миграции: внешние, люди без клуба, внешние с контактами или документами — для ручного разбора.
- Семьи-выпускники: членство родителей → «ушёл», история только на чтение. Подробно —
  [athletes-across-orgs.md](athletes-across-orgs.md).

**Проверка R2:** матрица доступа с осознанными изменениями; тест изоляции зелёный; отчёт по внешним разобран;
сквозные сценарии зелёные.

**Откат R2:** `ORGS_ROLES_SOURCE=legacy` и `ORGS_ENFORCE_SCOPING=false` возвращают прежнее поведение без
отката базы; старые поля всё ещё поддерживаются двойной записью.

### R3. Вход и администрирование

**4.5. Единый вход**
- `AuthIdentity` из `tg_id` и email. Вход через бота и ссылки `xfer` работают через новый модуль; для
  пользователя всё как раньше.
- Одноразовый код для заведения сессии на адресе организации. Центральный адрес входа — настройка
  `ORGS_CENTRAL_LOGIN_HOST`, пока пустая.
- Бот понимает организацию: `?start=<slug>`, по умолчанию «ksclub», выбор при нескольких членствах.

**4.6. Консоль платформы**
- `/platform/` для глобальных администраторов: организации (создать, приостановить), владельцы через
  приглашение, домены, журнал, режим поддержки и «войти как пользователь» с журналом.
- В интерфейсе появляется то, что сейчас делают в Django-админке (по журналу админки за год: удаление людей,
  пользователей и соревнований, изменение пользователей). После этого Django-админка — только глобальным
  администраторам.

**4.7. Администрирование организации**
- Настройки организации; сотрудники и роли; приглашения по ссылке и в боте; приостановка доступа.
- Очередь заявок участников вместо страницы «ожидает одобрения»: администратор подтверждает и связывает
  родителя с `Person`. Существующие ожидающие пользователи попадают в очередь.
- Журнал организации.

**4.8. Посетители**
- Публичные страницы (онлайн-результаты, заявки на соревнования) — по адресу организации, без членства.
- Вошедший пользователь без членства видит публичную часть и кнопку «Вступить / я родитель».

**Проверка R3:** вход через бота и `xfer` на staging и проде; администратор «ksclub» приглашает сотрудника и
подтверждает родителя в интерфейсе; Django-админка закрыта для всех, кроме глобальных администраторов;
сквозные сценарии зелёные.

**Откат R3:** старые страницы входа и «ожидает одобрения» остаются за флагом до R4.

### R4. Вторая организация и уборка

**4.9. Вторая организация**
- Демо-организация на `demo.ksclub.ru` (DNS-запись и сертификат на сервере). Тест изоляции и матрица на проде
  с двумя организациями. Пилотная реальная организация — по готовности.

**4.10. Уборка**
- Удалить чтения и двойную запись `is_approved`, групп как ролей и `TELEGRAM_*_IDS`; старые страницы входа
  и «ожидает одобрения».
- Неизвестный адрес → «организация не найдена» вместо «ksclub».
- Row-Level Security для внутренних таблиц.

**Проверка R4:** всё из R1–R3 плюс демо-организация полностью изолирована от «ksclub».

## Сквозные сценарии

Прогоняются автоматически на staging перед каждым релизом и выборочно вручную после выкатки.

1. Вход через Telegram-бота и по ссылке `xfer`; выход.
2. Новый пользователь из бота попадает в ожидание и подтверждается администратором.
3. Список спортсменов, карточка, редактирование.
4. Семья: состав, договоры, услуги, платежи, финансы.
5. Расписание: создание занятия, шаблоны недели, уведомление о занятии, отметка посещаемости.
6. Бот: меню родителя, тренера, менеджера; напоминания о тренировках.
7. Документы: загрузка, AI-анализ, привязка к спортсмену и соревнованию.
8. Соревнования: создание, заявка по ссылке, выгрузки xlsx и docx.
9. Онлайн-результаты: трансляция из XLSX, ручная правка, публичная страница, публикация в Telegram.
10. Уведомления: создание и рассылка.
11. Дедупликация людей.
12. Интеграции: синхронизация WhatsApp, API ассистента, задачи Celery по расписанию.
13. Права: родитель, тренер, менеджер, администратор видят ровно своё (матрица доступа).
14. Изоляция (с R2): данные второй организации не видны нигде.

## Готовность этапа 4

Этап считается выполненным, когда на проде:

- все сквозные сценарии работают для «ksclub»;
- все данные принадлежат организации, вторая организация полностью изолирована;
- роли хранятся только в базе, есть глобальные администраторы, владельцы и администраторы организаций;
- администратор организации управляет сотрудниками, ролями, приглашениями и заявками в интерфейсе;
- Django-админка доступна только глобальным администраторам;
- посетители видят публичные страницы и могут попроситься в организацию;
- внешние спортсмены и выпускники обработаны по правилам;
- старые механизмы ролей и входа удалены, тесты матрицы доступа и изоляции зелёные.

| Флаг | Что включает | Включается | Убирается |

## Риски и как их снимаем

| Риск | Защита |
|---|---|
| Забытый фильтр по организации — утечка данных | Тест изоляции, тест инвентаризации, позже RLS |
| Ошибка миграции ролей — кто-то потеряет доступ | Staging с копией прода, сверка отчёта и матрицы, откат флагом `ORGS_ROLES_SOURCE` |
| Задачи по расписанию или бот без организации | Явный `organization_id`, тесты на каждую задачу и обработчики бота |
| Сотрудники теряют нужное в Django-админке | Перенос действий из журнала админки в интерфейс до закрытия (R3) |
| Внешние спортсмены пропадут из заявок | Пометка, а не удаление; заявки и результаты не фильтруются по пометке; сквозной сценарий 8 |
